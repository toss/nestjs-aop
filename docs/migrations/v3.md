# Migrating to v3

v3 ships one ESM build and changes the supported Node.js and testing toolchains.
NestJS 10, 11 and 12 remain supported with the requirements below. Existing
NestJS starter projects may need compiler and Jest configuration changes.

## Breaking changes

- Node.js 22.12.0 or later is required. CI tests Node 22.12.0, 24.19.0 and 26.10.0.
- NestJS 8 and 9 are no longer supported. Use v2 if you cannot upgrade yet.
- The package contains one ESM build, not separate ESM and CommonJS builds.
- Only the root entry is exported. Replace
  undocumented `dist/*` or `src/*` imports with imports from `@toss/nestjs-aop`.
- Older CommonJS Jest setups need migration even if the application itself runs.

NestJS 10, 11 and 12 and the existing decorator runtime API remain supported.
The npm tarball includes only built `dist` files plus npm-required metadata,
README and license. Source TypeScript, tests and this migration guide stay in the
repository. JavaScript source maps embed their original source; declaration maps
are disabled because the source tree is not shipped.

Package version, runtime Node version, TypeScript module mode and Jest loader
settings are independent compatibility dimensions.

## Application imports

```ts
import { AopModule, Aspect, createDecorator } from '@toss/nestjs-aop';
import type { LazyDecorator, WrapParams } from '@toss/nestjs-aop';
```

For an ESM TypeScript application, set `"type": "module"` in its package.json and
use `"module": "NodeNext"` and `"moduleResolution": "NodeNext"`. Include `.js`
extensions in local relative imports. Preserve `experimentalDecorators` and
`emitDecoratorMetadata` for Nest's legacy decorators and dependency injection.

CommonJS applications may use `require('@toss/nestjs-aop')` on the supported Node
versions. This loads the same synchronous ESM artifact; it is not a CJS build.
Do not infer Jest compatibility from a successful native Node `require()` call.
On Node 22.12.0, `require(esm)` emits an `ExperimentalWarning`; the application
still runs. In the Node 22 line, 22.13.0 removes that default warning; the tested
Node 24/26 releases do not emit it either.

### TypeScript consumers

The compiler requirement depends on how the application emits its imports:

- **ESM application:** NodeNext with `type: module` (or `.mts`) works. Both
  TypeScript 5.7.3 and 5.8.3 are covered by the packed-consumer checks.
- **CommonJS application with NodeNext:** use **TypeScript 5.8 or later**.
  TypeScript 5.7 rejects the generated `require(esm)` with TS1479 even when the
  installed Node version can execute it.
- **CommonJS application with `module: node16` or `node18`:** these modes model
  older Node interop and reject `require(esm)`. Upgrade to NodeNext with TS >= 5.8,
  or migrate the application to ESM. Updating Node alone does not fix this error.
- **Existing `module: commonjs` + `moduleResolution: node`/`node10`:** the top-level
  `types` field keeps the legacy resolver working. TypeScript 5.7.3 and 5.8.3 are
  checked in this mode; the emitted application still needs the supported Node
  runtime. This is an existing-project compatibility path, not a recommendation
  to switch a new project away from Node-aware module resolution.

These are separate from the Jest requirements below. A successful `tsc` build
and native application startup do not establish that a default CJS Jest setup
will work.

## Jest: portable ESM setup

Configure the transformer to emit ESM and launch Jest with VM modules enabled.
For a TypeScript consumer with ts-jest, the following configuration is tested
against the packed package with Jest 29.7.0 and 30.4.2 / ts-jest 29.4.12.
CI checks that this example exactly matches the configuration it runs:

```js
// jest.config.cjs (the .cjs extension also works in a type:module project)
module.exports = {
  testMatch: ['**/*.test.ts'],
  extensionsToTreatAsEsm: ['.ts'],
  transform: {
    '^.+\\.ts$': [
      'ts-jest',
      {
        useESM: true,
        tsconfig: {
          module: 'ESNext',
          moduleResolution: 'Bundler',
          esModuleInterop: true,
          experimentalDecorators: true,
          emitDecoratorMetadata: true,
        },
      },
    ],
  },
};
```

```sh
node --experimental-vm-modules node_modules/jest/bin/jest.js
```

When local source imports use `.js` extensions but point to TypeScript source,
configure the transform/resolver for that layout. The library's source tests use
`moduleNameMapper: { '^(\\.{1,2}/.*)\\.js$': '$1' }`. Do not remap package imports
to this repository's source in consumer tests: verify the installed package.

In ESM tests, import `jest` from `@jest/globals` when needed. ESM mock setup differs
from CJS `jest.mock`; review Jest's `jest.unstable_mockModule` guidance rather than
assuming existing module mocks are unchanged.

### Keeping CommonJS Jest tests

Upgrading to Jest 30 is not required if you use the ESM setup above. If you want
to retain CJS test output instead, the tested combination is Jest 30.4.2 with
Node >= 24.9 and `--experimental-vm-modules`. Jest 29 CJS output still fails
with that flag. On Node 22, use ESM test output. Mocking ESM dependencies still
requires ESM-aware mocks even when the test file itself is CommonJS.

## Tested compatibility

The packed candidate is installed into independent consumers with Nest
10.4.22, 11.2.6 and 12.1.0. Each is checked on Node 22.12.0, 24.19.0 and 26.10.0.

- Native ESM and CommonJS: actual Nest application bootstrap, aspect execution,
  before/original/after ordering, return values, undecorated methods, lifecycle
  completion and repeated calls pass.
- Jest 30.4.2 ESM with `--experimental-vm-modules`: passes on all tested nodes.
- Jest 30.4.2 CJS with that flag: passes on tested Node 24/26; fails on Node 22.12.0.
  Use the ESM setup on Node 22.
- TypeScript 5.8.3 NodeNext `.mts` and `.cts`, TypeScript 5.7.3 NodeNext `.mts`,
  and both versions in CommonJS/node10 mode pass with `skipLibCheck: false`,
  including decorator metadata settings. CI also checks the expected TS1479
  failures for TS 5.7.3 CJS/NodeNext and TS 5.8.3 CJS/node16.
- The exact ts-jest ESM configuration above bootstraps Nest, injects dependencies,
  and checks aspect ordering, return values, lifecycle and repeated calls with
  Jest 29.7.0 and 30.4.2.

- With Nest 11.2.6, ts-jest 29.4.12 and Node 24.19.0, Jest 29.7.0 CJS fails
  even with the VM flag; switching its transformer/test mode to ESM passes.
  Jest 30.4.2 CJS and ESM configurations pass with the same VM flag.

These are exact tested versions, not a claim that every earlier Jest or
TypeScript version works. The same VM flag is required for the tested newer CJS
Jest configuration. A default CJS Jest command without it is not supported here.

Alongside the reproducible matrix, CI checks baseline Nest releases
10.0.0 / 11.0.0 / 12.0.1 and latest releases matching `^10` / `^11` / `^12` on
Node 24.19.0. These cases exercise the installed package rather than claiming
that every historical patch and toolchain combination is covered. The Nest 10.0.0
minimum case uses `skipLibCheck: true` because that release has upstream TS2416
errors in its file-validator declarations; the pinned and latest Nest cases keep
`skipLibCheck: false`. The application import/compiler-boundary checks still run
for that minimum case. Nest 12.0.0 has inconsistent package peers
(`@nestjs/core@12.0.0` requires `@nestjs/common@^11`), so the baseline uses the
corrected 12.0.1 pair without bypassing peer validation.

The compatibility CI installs the tarball and independent peer dependencies,
not symlinked workspace source. Run the same check after building:

```sh
pnpm pack --out /tmp/nestjs-aop.tgz
npm run test:packed -- /tmp/nestjs-aop.tgz 12.1.0
```

The verifier uses the current Node executable. Run it through `npm run test:packed` on
Windows so it can invoke the npm CLI without executing a `.cmd` shim or shell.
Use a platform-appropriate tarball path in the commands above.

## v2.2.0 baseline

Before this migration, the published npm 2.2.0 package was installed with Nest
12.1.0 in a fresh consumer. Native CJS and ESM apps passed on Node 24.19.0.
Jest 30.4.2 CJS passed with the VM flag. Its ESM static-import consumer hit a Jest
mixed CJS/ESM loader error; sequentially awaiting imports of `@nestjs/common` and
`@nestjs/core` before dynamically importing the consumer avoided that error.
The v3 packed ESM artifact passes the static-import ESM Jest fixture directly.
